# ExpenseFlow — Architecture

PoC expense submission and approval API. One user journey: submit an expense, convert it
to base currency (INR), approve or reject it. No auth/user concept is in scope; FX
conversion happens synchronously at submission time; approve/reject is a single
state-transition endpoint. A secondary read-only endpoint generates spending insights
via the Claude API.

## 1. SQLite schema — `expenses` table

```sql
CREATE TABLE expenses (
    id                 INTEGER PRIMARY KEY AUTOINCREMENT,
    submitted_by       TEXT    NOT NULL,
    description        TEXT    NOT NULL,
    amount_minor       INTEGER NOT NULL,
    currency           TEXT    NOT NULL,
    category           TEXT    NOT NULL,
    amount_base_minor  INTEGER NOT NULL,
    fx_rate            REAL    NOT NULL,
    status             TEXT    NOT NULL DEFAULT 'pending'
                        CHECK (status IN ('pending', 'approved', 'rejected')),
    created_at         TEXT    NOT NULL,
    decided_at         TEXT,
    decided_by         TEXT
);
```

| Column | Type | Why |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | Surrogate key; stable reference for GET/PATCH by id. |
| `submitted_by` | TEXT NOT NULL | Free-text name/email of who submitted. No `users` table since there's no auth — this is descriptive, not a foreign key. |
| `description` | TEXT NOT NULL | What the expense was for; required so approvers have context to decide. |
| `amount_minor` | INTEGER NOT NULL | Original submitted amount in minor units (paise/cents) of `currency`. Integer per the "money is never float" rule; preserves exactly what the submitter entered, independent of any conversion. |
| `currency` | TEXT NOT NULL | ISO 4217 code of the original amount (e.g. `"USD"`). Needed to know what `amount_minor` is denominated in and to know whether an FX call is even required. |
| `category` | TEXT NOT NULL | Free-text expense category (e.g. `"rooms"`, `"meals"`); used to filter `GET /expenses` and to group the spending insights. |
| `amount_base_minor` | INTEGER NOT NULL | `amount_minor` converted to INR minor units at submission time. This is the figure approvals and any future reporting/sums operate on, since base currency is INR per the brief. |
| `fx_rate` | REAL NOT NULL | The rate used for the conversion (`amount_base_minor / amount_minor`, currency-adjusted). Not itself money, so a float is acceptable — it exists purely as an audit trail so a stored conversion is reproducible/explainable later, not recomputed from a rate that may have since moved. |
| `status` | TEXT NOT NULL DEFAULT 'pending', CHECK constraint | Drives the state machine (`pending → approved` / `pending → rejected`). CHECK constraint enforces valid values at the DB layer, not just in application code. |
| `created_at` | TEXT NOT NULL | ISO-8601 submission timestamp. Audit trail / ordering; set once, never updated. |
| `decided_at` | TEXT, nullable | ISO-8601 timestamp of the approve/reject decision. NULL while `pending`. |
| `decided_by` | TEXT, nullable | Free-text name/email of who decided, mirroring `submitted_by`. NULL while `pending`. |

No separate `currencies` or `users` tables — out of scope per the brief: the one journey
doesn't need them, and CLAUDE.md says not to invent endpoints beyond the brief, which
extends to not inventing supporting entities the journey doesn't need.

## 2. Endpoints

| Method | Path | Request body | Response |
|---|---|---|---|
| `POST` | `/expenses` | `{"submitted_by", "description", "amount_minor", "currency", "category"}` | `201` — full expense object with `id`, `amount_base_minor`, `fx_rate`, `status: "pending"` |
| `GET` | `/expenses` | — (optional query params `status`, `category`) | `200` — JSON array of expense objects |
| `GET` | `/expenses/{id}` | — | `200` — single expense object, or `404` if not found |
| `PATCH` | `/expenses/{id}/status` | `{"status": "approved"\|"rejected", "decided_by"}` | `200` — updated expense object; `404` if not found; `409` if not currently `pending` |
| `GET` | `/reports/insights` | — | `200` — `{"insight": {"summary": str, "bullets": [str, str, str]}}`, generated by the Claude API over all expenses |

Expense object shape (the first four endpoints return this):

```json
{
  "id": 1,
  "submitted_by": "jane@company.com",
  "description": "Client dinner",
  "amount_minor": 450000,
  "currency": "USD",
  "category": "meals",
  "amount_base_minor": 450000,
  "fx_rate": 1.0,
  "status": "pending",
  "created_at": "2026-08-11T10:15:00Z",
  "decided_at": null,
  "decided_by": null
}
```

Notes:
- `POST /expenses` currently stubs FX conversion: `fx_rate` is hardcoded to `1.0` and
  `amount_base_minor` always equals `amount_minor`, regardless of `currency`. There is no
  external rate provider call yet — `routes.py` has a `TODO` marking where a real lookup
  (`currency` → INR) would replace the hardcoded rate.
- `GET /reports/insights` calls the Claude Messages API with a summary of all expenses and
  asks for a JSON insight object; on any API/parsing failure it retries once, then falls
  back to a safe default rather than raising.

Five endpoints total: submit+convert, list, fetch, decide, plus one read-only insights
endpoint over the same data.

## 3. File layout

```
app/
  main.py     - FastAPI app instance, startup (create tables), router registration.
  db.py       - SQLAlchemy engine/session setup for the SQLite file (expenseflow.db),
                get_db dependency.
  models.py   - SQLAlchemy ORM model for Expense (maps to the expenses table above).
  schemas.py  - Pydantic v2 request/response models: ExpenseCreate, ExpenseOut,
                ExpenseStatusUpdate.
  routes.py   - The 5 endpoints above; orchestrates schema validation, the (currently
                stubbed) FX conversion, ORM calls, and status-transition checks.
  insights.py - Calls the Claude Messages API to turn a list of expenses into a
                structured {"summary", "bullets"} insight object, with retry-once and
                a safe fallback on failure.
```

No `fx.py` or `config.py` yet — the real FX provider lookup named in CLAUDE.md's stack
(httpx) hasn't been implemented; `POST /expenses` stubs the rate at `1.0` for now (see the
note under the endpoints table). No `tests/` directory exists yet either.

## 4. Edge-case decisions

The two FX-related decisions below (#1, #2) describe the planned behavior for when a real
FX provider lookup is implemented — `routes.py` currently stubs `fx_rate = 1.0` for every
currency (see the `TODO` there), so neither is active yet.

### 1. FX provider is slow, down, or returns no rate for the currency (planned)
Since conversion would happen synchronously inside `POST /expenses`, an FX outage would
otherwise either hang the request or corrupt data (e.g. a defaulted rate of 1.0 silently
mispricing a USD expense as INR).

**Decision:** once a real FX client exists, it should set a strict httpx timeout; on
timeout, non-2xx, or unrecognized currency, `POST /expenses` should return `502 Bad
Gateway` and write nothing (no partial row — the DB insert only happens after a
successful rate lookup). The submitter retries the same request; no expense exists in a
half-converted state. `currency == "INR"` should bypass the external call entirely, so the
common case isn't exposed to this failure at all.

### 2. Rounding drift when converting minor units by a float rate (planned)
`amount_base_minor = amount_minor * fx_rate` is a float multiplication that rarely lands
on an integer. Truncating inconsistently (sometimes floor, sometimes round) makes sums of
approved expenses not reconcile, and is exactly the kind of float-creep the "money is
never float" rule exists to prevent.

**Decision:** once real conversion is implemented, define one rounding rule at the
boundary — round-half-up to the nearest integer minor unit, applied in exactly one place —
and always store the resulting `amount_base_minor` as `INTEGER`. `fx_rate` is stored
alongside so the exact conversion is auditable/reproducible even though the rate itself
may drift over time.

### 3. Concurrent or repeated approve/reject calls on the same expense
Two `PATCH /expenses/{id}/status` calls racing (e.g. two approvers), or a client retrying
a request that already succeeded, could otherwise apply a second decision (approving an
already-rejected expense, or overwriting `decided_by`).

**Decision:** the transition is enforced as a single conditional `UPDATE ... WHERE id = :id
AND status = 'pending'`, checking the affected row count rather than doing a read-then-write.
If zero rows were updated, the expense either doesn't exist (`404`) or is no longer `pending`
(`409 Conflict`), and the response tells the caller which. This makes the state machine
atomic at the DB layer instead of relying on an application-level check-then-act that a
race can slip through.
